# Тесты в TypeScript: стек, браузер, моки, типы, покрытие

Какой тестовый стек брать для проектов на TypeScript любого вида: сайты и приложения с компонентами, игры и визуализации, библиотеки и инструменты. Разобраны Vitest 5 и его браузерный режим, статус Jest, Playwright, Testing Library, Storybook, MSW 3, fast-check, Stryker, тесты типов (expect-type, tsd, tstyche и ловушка ложно-зелёного `typecheck` в Vitest), покрытие (v8 или istanbul) и визуальная регрессия. Состояние знаний: ноябрь 2026. Версии из `npm view` на 8 ноября 2026: vitest 5.1.0, jest 30.5.2, playwright 1.65.0, storybook 10.6.6, msw 3.0.4, fast-check 4.10.2, @stryker-mutator/core 10.1.1, expect-type 1.4.0, tsd 0.33.0, tstyche 7.2.5, typescript 7.0.2. Пометка `[проверено локально]` означает проверку запуском на Windows 11, Node 24.17, Chrome 156, Vitest 5.1 и TypeScript 7.0.2. Пометка `[устарело]` указывает замену, `[не проверено]` значит опору на один вторичный источник. Замеры скорости и размера описаны в [benchmarking.md](benchmarking.md), настройка сборки и CI — в [toolchain.md](toolchain.md), сами типы и их паттерны — в [types-patterns.md](types-patterns.md), общий цикл разработки с ревью — в [pipeline.md](pipeline.md).

## Выбор стека

Вывод: для новых проектов стандартный набор — Vitest 5 для unit и компонентных тестов (в браузерном режиме для всего, что требует настоящего DOM), Playwright для сквозных сценариев, MSW 3 для сети, fast-check и Stryker для проверки силы тестов. Типы проверяйте через `expectTypeOf` Vitest либо tstyche; tsd отстаёт от TS 7.

| Задача | Выбор | Замечание |
| --- | --- | --- |
| Unit-тесты и логика | Vitest 5 | Node 22.12 и выше, Vite 6.4 и выше |
| Компоненты с DOM | Vitest browser mode с провайдером `playwright` | настоящий браузер вместо эмуляции |
| Истории и интерактивные сценарии компонентов | Storybook 10 + `@storybook/addon-vitest` | истории исполняются как Vitest-тесты |
| Сквозные сценарии | Playwright 1.65 | трейсы, скриншоты, несколько браузеров |
| Запросы к элементам | Testing Library, `getByRole` | `getByTestId` в последнюю очередь |
| Сеть | MSW 3 | только ESM, Node 22 и выше |
| Входы, которые не придумать вручную | fast-check 4 | сжатие контрпримеров |
| Сила тестов | Stryker 10 | браузерный режим Vitest не поддерживается |
| Тесты типов | `expectTypeOf` из Vitest, tstyche | tsd привязан к компилятору 5.9 |
| Покрытие | v8 по умолчанию, istanbul вне V8 | см. [Покрытие](#покрытие) |
| Существующий проект на Jest | остаться на Jest 30 | миграция не обязательна |

Jest: версия 30.5.x остаётся текущей (релиз 30.0 в июне 2025). Авторы заявляют более частые мажоры, план на Jest 31 не назван — [Jest blog](https://jestjs.io/blog). Jest не `[устарело]`: если проект уже на нём и тесты стабильны, переписывать их ради смены раннера не нужно. Для нового проекта выбирайте Vitest: он использует конфигурацию Vite, исполняет TypeScript без отдельной трансформации и имеет браузерный режим.

Тесты, которые должны жить рядом с выбором стека:

- Для библиотек с поддержкой нескольких версий TypeScript добавляйте tstyche (матрица версий через `--target`).
- Для игр и визуализаций выносите вычислительное ядро (симуляция, геометрия, парсеры) в чистые функции и покрывайте их unit-тестами в Node. Отрисовку покрывайте скриншотами в браузерном режиме.
- Для контентных сайтов основной вес на сквозных сценариях Playwright и визуальных проверках страниц; логику сборки данных тестируйте unit-тестами.

## Vitest

Вывод: Vitest 5 требует Node 22.12 и выше и Vite 6.4 и выше, `vite` теперь обязательный peer. В 5.0 сменились провайдеры браузерного режима, строгость локаторов и сравнение текста, перенесён формат бенчмарков. Релиз 5.0 вышел 3 сентября 2026 — [Vitest 5 announcement](https://v5.cn.vitest.dev/blog/vitest-5).

### Что изменилось в 5.0

- Требования: Node 22.12 и выше, Vite 6.4 и выше, `vite` обязательный peer. Провайдер `@vitest/browser-webdriverio` передан сообществу. `browser.locators.exact` по умолчанию строгий, `toHaveTextContent` сравнивает текст точно — [Vitest Migration Guide](https://vitest.dev/guide/migration).
- Бенчмарки: `bench` стал фикстурой внутри `test()`; удалены `bench.skip/only/todo`, `benchmark.reporters`, `benchmark.outputFile`, `benchmark.compare`, `--compare`, `benchmark.outputJson`, `--outputJson`. Вместо них `--reporter=json --outputFile=<путь>`, `writeResult` и `bench.from()` — [Vitest Migration Guide](https://vitest.dev/guide/migration). Подробно о замерах — [benchmarking.md](benchmarking.md).
- Появился Trace View (`browser.traceView: true`), он не требует провайдера. Браузерный режим быстрее на 16–18% — [Vitest 5 announcement](https://v5.cn.vitest.dev/blog/vitest-5).

Если после обновления с 4.x падают тесты на `toHaveTextContent`, причина обычно в точном сравнении: подстрока больше не совпадает. Меняйте ожидание на полный текст, а не отключайте проверку.

### Браузерный режим

Провайдеры: `playwright` (рекомендован), `webdriverio`, `preview`. Провайдер `preview` только симулирует события и для CI не рекомендован. Установка: `@vitest/browser-playwright`. Конфиг: `browser: {enabled: true, provider: playwright(), instances: […]}` — [Vitest Browser Mode](https://vitest.dev/guide/browser/).

`[проверено локально]` Рабочий конфиг с установленным в систему Chrome:

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config'
import { playwright } from '@vitest/browser-playwright'

export default defineConfig({
  test: {
    browser: {
      enabled: true,
      provider: playwright({ launchOptions: { channel: 'chrome' } }),
      instances: [{ browser: 'chromium' }],
    },
  },
})
```

Что нужно знать про браузерный режим:

| Тема | Правило |
| --- | --- |
| Мутационное тестирование | Stryker не поддерживает браузерный режим Vitest; для таких тестов нужны unit-тесты в Node или ручной выборочный обзор |
| Бенчмарки | Шаг таймера 100 мкс даёт `p50 = 0` на коротких функциях; нулевая медиана здесь ошибка замера, см. [benchmarking.md](benchmarking.md) |
| Шардирование | Подробные настройки sharding браузерного режима в документации не описаны |
| Несколько браузеров | `instances` задаёт список; для бенчмарка есть `perProject: true` (chromium, firefox, webkit) |
| Отладка | Trace View (`browser.traceView: true`) |

### Типизированные утверждения и тесты типов

В Vitest есть `expectTypeOf` (обёртка над `expect-type`) и режим `typecheck`. Здесь есть опасная ловушка, подробно описанная в [Тесты типов](#тесты-типов): при неверном `typecheck.tsconfig` ошибка в типе даёт зелёный результат.

### Бенчмарки внутри Vitest

`vitest bench` и `expect(a).toBeFasterThan(b, {delta})` подходят для сравнения реализаций, но не для регрессионных порогов в CI на шумных раннерах. Правила и команды — в [benchmarking.md](benchmarking.md).

## E2E и браузер

Вывод: сквозные сценарии пишите на Playwright, компоненты проверяйте в браузерном режиме Vitest или через истории Storybook. Запросы к элементам делайте по роли и доступному имени. Визуальные снимки сравнивайте только в той же среде, где они получены.

### Testing Library

Приоритет запросов: сначала `getByRole`, `getByTestId` в последнюю очередь; `findBy*` ждёт с таймаутом 1000 мс по умолчанию — [About Queries](https://testing-library.com/docs/queries/about). Тест, который ищет элемент по роли, заодно проверяет доступность. Увидев `getByTestId` там, где есть роль, просите заменить.

### Playwright

- Трейсы Playwright — средство отладки: действия, снимки DOM, сеть. Параметр `trace: 'on'` «not recommended as it's performance heavy» — [Trace viewer](https://playwright.dev/docs/trace-viewer). В запущенном трейсе замеры смещены, поэтому в тестах скорости трейс выключайте.
- CDP-сессия и `browser.startTracing` доступны только в Chromium — [Browser API](https://playwright.dev/docs/api/class-browser). Тест, использующий CDP, не пройдёт в Firefox и WebKit.
- Playwright WebKit в измерениях не проверялся (браузер не был установлен).

### Storybook

Storybook 10: основной путь — `@storybook/addon-vitest`, истории исполняются как Vitest-тесты в браузерном режиме; test-runner описан как запасной вариант — [Storybook Testing](https://storybook.js.org/docs/writing-tests). `@storybook/addon-vitest` 10.6.6 требует `vitest ^4 || ^5` (`npm view`). Интерактивные тесты в историях (`play`-функции) удобны для компонентов с состояниями, потому что одна история служит и документацией, и тестом.

### Визуальная регрессия

| Инструмент | Что настраивается | Правила |
| --- | --- | --- |
| Playwright `toHaveScreenshot` | `threshold` (по умолчанию 0,2), `maxDiffPixels`, `stylePath` | базовые снимки зависят от ОС и браузера, сравнивать нужно в той же среде — [Visual comparisons](https://playwright.dev/docs/test-snapshots) |
| Vitest `toMatchScreenshot` | pixelmatch, `threshold`, `allowedMismatchedPixelRatio`, собственные сравнители | снимки по браузеру и платформе; эталоны генерировать в CI, а не локально; маскирование, отключение анимаций, ожидание `document.fonts.ready` — [Visual Regression Testing](https://vitest.dev/guide/browser/visual-regression-testing) |

Практика для визуальных тестов: отключайте анимации, маскируйте динамические области (даты, счётчики, случайные данные), дожидайтесь шрифтов, фиксируйте размер окна. Для игр и визуализаций с WebGL или Canvas используйте детерминированный источник случайных чисел и фиксированный кадр симуляции; различия между GPU и драйверами делают сравнение между машинами ненадёжным, поэтому эталоны получайте на той же машине или образе CI, который их проверяет. Это общий вывод, а не результат измерения `[не проверено]`.

## Моки и сеть

Вывод: сеть мокайте на границе процесса через MSW 3, а не подменой `fetch` в каждом тесте. MSW 3 вышел 28 сентября 2026 и ломает совместимость с 2.x.

### MSW 3

MSW 3.0.0 (2026-09-28), версия 3.0.4 на ноябрь 2026 — [MSW Releases](https://github.com/mswjs/msw/releases):

| Изменение | Что делать при миграции |
| --- | --- |
| Только ESM, Node 22 и выше, TypeScript 5.9 и выше | проверить `engines` и модульную систему проекта |
| `handleRequest()` удалён в пользу `defineNetwork()` | переписать низкоуровневый вызов |
| `onUnhandledRequest` переименован в `onUnhandledFrame` | заменить имя опции |
| Cookies в Node больше не управляются | задавать заголовки `Cookie` и `Set-Cookie` явно |
| `setTimeout` больше не патчится | не рассчитывать на ускорение таймеров внутри MSW |

### Правила моков

- Мок описывает контракт внешней системы, а не внутреннее устройство вызывающего кода. Тест не должен ломаться при переименовании приватной функции.
- Один набор обработчиков MSW используйте и в unit-тестах, и в Storybook, и в сквозных тестах, чтобы мок не расходился с поведением.
- Неописанный запрос должен падать, а не уходить в сеть: включите режим ошибки при необработанном запросе (в MSW 3 опция называется `onUnhandledFrame`).
- Фейковые таймеры нужны для кода с задержками; проверяйте, что тест не зависит от реального времени.

Подробный разбор мок-стратегий для серверного кода на Node — в скилле node-knowledge.

## Property-based и мутационное тестирование

Вывод: fast-check находит входы, которые вы не придумали, и сжимает их до минимального контрпримера. Stryker показывает, какие изменения кода тесты не замечают. Stryker не работает с браузерным режимом Vitest.

### fast-check

- Генерация случайных входов и сжатие контрпримеров — [fast-check Introduction](https://fast-check.dev/docs/introduction/).
- Планировщик `fc.scheduler()` с `schedule`, `scheduleFunction`, `waitFor` находит гонки в асинхронном коде — [Race conditions](https://fast-check.dev/docs/advanced/race-conditions/).
- `@fast-check/vitest` 0.4 совместим с Vitest 4.1+ и 5 — [@fast-check/vitest](https://github.com/dubzzz/fast-check/tree/main/packages/vitest).

Где применять: разбор и сериализация (round-trip), нормализация, геометрия и математика, структуры данных, редьюсеры состояния, парсеры форматов, игровая логика с инвариантами (сохранение количества ресурсов, отсутствие пересечений). Типичные свойства: обратимость (`decode(encode(x)) == x`), идемпотентность, монотонность, сохранение инварианта после любой последовательности операций. Начинайте с одного свойства на функцию и сохраняйте найденные контрпримеры как обычные регрессионные тесты.

### Stryker

- Раннер Vitest: анализ покрытия только `perTest`, браузерный режим Vitest не поддерживается — [Vitest Runner](https://stryker-mutator.io/docs/stryker-js/vitest-runner/). Peer `vitest >=2.0.0` (`npm view`).
- `--incremental` хранит результаты в `reports/stryker-incremental.json`; изменения вне мутируемых и тестовых файлов не отслеживаются — [Incremental](https://stryker-mutator.io/docs/stryker-js/incremental/). Поэтому при смене конфигурации, зависимостей или версии TS инкрементальный файл удаляйте.
- Stryker не заменит проверку силы браузерных компонентных тестов. Для них держите логику в unit-тестах Node или проверяйте тесты ручным выборочным обзором.
- Мутационный прогон дорог: запускайте его по изменённым файлам или раз в сутки, а не на каждый коммит.

Читайте выживших мутантов как список пропущенных проверок: сначала добавляйте утверждение на границы условий и возвращаемые значения, а не увеличивайте число тестов.

## Тесты типов

Вывод: тест типов должен уметь падать. Режим `typecheck` Vitest даёт ложно-зелёный результат, если его `tsconfig` не включает файлы тестов. Добавьте в CI отрицательный контрольный тест. tsd привязан к компилятору 5.9 и не проверяет типы TS 6 или 7.

### Инструменты

| Инструмент | Что делает | Ограничения |
| --- | --- | --- |
| `expect-type` 1.4.0 (`expectTypeOf`) | Проверки на этапе компиляции; без зависимостей; Vitest экспортирует `expectTypeOf` | Ограничения с пересечениями, обобщёнными функциями и перегрузками — [expect-type](https://github.com/mmkal/expect-type) |
| `tsd` 0.33.0 | `expectType` (строго), `expectAssignable`, `expectError` | Зависит от `@tsd/typescript ^5.9.2` (`npm view`): типы проверяются компилятором 5.9, а не TS 6 или 7. Последний push 2025-08 (`gh api`) — [tsd](https://github.com/tsdjs/tsd) |
| `tstyche` 7.2.5 | `--target '>=5.6'` для прогона на нескольких версиях TS; матчеры `.toBe`, `.toBeAssignableTo`, `.toBeCallableWith` и другие; проверка сообщений подавленных ошибок | peer `typescript: >=5.4` (`npm view`) — [tstyche](https://github.com/tstyche/tstyche) |

Для библиотек с поддержкой нескольких версий TS tstyche полезнее tsd: `--target` покрывает матрицу версий, а tsd заперт на встроенном компиляторе. Поддержка TS 7 в tstyche и tsd на практике не проверялась, документация вопроса не освещает.

### Ловушка ложно-зелёного typecheck в Vitest

`[проверено локально]` `vitest run --typecheck.only` с TS 7.0.2 печатает «Testing types with tsc and vue-tsc is an experimental feature».

| Конфигурация | Результат неверного `expectTypeOf('a').toEqualTypeOf<number>()` |
| --- | --- |
| `typecheck.tsconfig` с `include: ["src"]`, файлы тестов не входят | зелёный (`success: true`): ошибка не обнаружена |
| Свой tsconfig с `include: ["*.ts"]`, файл теста входит | падает: `Type 'number' does not satisfy the constraint '"Expected number, Actual string"'` |

Защита:

1. Проверьте, что `include` в `typecheck.tsconfig` покрывает файлы тестов типов (по умолчанию имена вида `*.test-d.ts`).
2. Добавьте в набор отрицательный контрольный тест: утверждение, которое заведомо неверно, внутри `// @ts-expect-error` и ожидаемое как ошибка. Если контрольный тест не падает при его снятии, прогон ложно-зелёный.
3. Проверяйте, что число найденных файлов тестов типов в отчёте не нулевое.

```ts
// types.test-d.ts
import { expectTypeOf, test } from 'vitest'

test('guard: typecheck реально проверяет этот файл', () => {
  // @ts-expect-error: если ошибки нет, значит typecheck не видит файл
  expectTypeOf('a').toEqualTypeOf<number>()
})

test('parse возвращает число', () => {
  expectTypeOf(parse('1')).toEqualTypeOf<number>()
})
```

Режим `typecheck` Vitest помечен как экспериментальный, поэтому для публичных библиотек надёжнее запускать проверку типов отдельным шагом CI (`tsc --noEmit` по каталогу тестов типов или tstyche). Время и стоимость проверки типов — в [benchmarking.md](benchmarking.md), паттерны типов — в [types-patterns.md](types-patterns.md).

## Покрытие

Вывод: Vitest по умолчанию использует `v8`. С версии 3.2 ремаппинг на AST даёт «identical coverage reports to Istanbul». V8 быстрее и не требует предкомпиляции, но не работает вне V8 (Firefox, Bun). Istanbul работает везде и медленнее — [Vitest Coverage](https://vitest.dev/guide/coverage).

| Критерий | v8 | istanbul |
| --- | --- | --- |
| Скорость | быстрее | медленнее |
| Предкомпиляция | не нужна | нужна инструментация |
| Среды | только V8 (Chromium, Node) | везде, включая Firefox и Bun |
| Подсказки игнорирования | нужен `@preserve` | обычные комментарии |
| Пакет | `@vitest/coverage-v8` | `@vitest/coverage-istanbul` |

Правила:

- Выбирайте `v8`, если тесты идут только в Node и Chromium. Берите `istanbul`, если нужны Firefox, WebKit или Bun.
- Подсказки игнорирования (`/* v8 ignore next */`) нуждаются в `@preserve`, иначе транспилятор удалит комментарий.
- Покрытие строк показывает, что код выполнялся, а не что результат проверен. Силу тестов проверяет Stryker, см. [Property-based и мутационное тестирование](#property-based-и-мутационное-тестирование).
- Порог покрытия задавайте на изменённый код и на критичные модули, а не одной цифрой на весь репозиторий: общая цифра смещается от генерируемых файлов и конфигов.
- Не смешивайте покрытие браузерного и Node-прогонов без слияния отчётов; следите, что браузерные тесты не пропали из отчёта.

## Чеклист ревью тестов

Каждый пункт можно проверить по diff.

Выбор и настройка

- [ ] Раннер и версия соответствуют проекту; Node не ниже 22.12 для Vitest 5.
- [ ] Для компонентов с DOM используется браузерный режим или Storybook, а не ручная эмуляция.
- [ ] Провайдер браузерного режима `playwright`, а не `preview` в CI.
- [ ] После обновления Vitest до 5.x ожидания `toHaveTextContent` проверены на точное сравнение.

Содержание тестов

- [ ] Тест падает, если убрать проверяемую логику (проверено вручную или Stryker).
- [ ] Утверждения проверяют результат и границы, а не только вызов функции без ошибки.
- [ ] Запросы к элементам по роли (`getByRole`); `getByTestId` оправдан в комментарии.
- [ ] Нет зависимости от реального времени, порядка тестов и сети.
- [ ] Асинхронные ожидания используют `findBy*` или явный `waitFor`, а не `sleep`.

Сеть и моки

- [ ] Сеть мокается через MSW; необработанный запрос приводит к ошибке (`onUnhandledFrame` в MSW 3).
- [ ] Мок описывает внешний контракт, а не внутренние функции.
- [ ] Миграция MSW 2 на 3 учла только ESM, `defineNetwork()` и управление cookies.

Типы

- [ ] `typecheck.tsconfig` включает файлы тестов типов.
- [ ] Есть отрицательный контрольный тест, который заведомо падает без `@ts-expect-error`.
- [ ] Для библиотек с несколькими версиями TS задан матричный запуск (`tstyche --target`).
- [ ] Не используется tsd как единственная проверка при TS 6 или 7.

Покрытие и сила

- [ ] Провайдер покрытия соответствует среде (`v8` или `istanbul`), подсказки игнорирования содержат `@preserve`.
- [ ] Порог покрытия задан на изменённый код.
- [ ] Для логики с инвариантами есть property-тест (fast-check), найденные контрпримеры сохранены.
- [ ] Результаты Stryker читаются по выжившим мутантам; `stryker-incremental.json` сброшен после смены конфигурации.

Визуальные и E2E-тесты

- [ ] Снимки получены и сравниваются в одной среде (ОС, браузер); эталоны Vitest сгенерированы в CI.
- [ ] Анимации отключены, динамические области замаскированы, шрифты загружены (`document.fonts.ready`).
- [ ] Трейс Playwright не включён в тестах, где мерится скорость.
- [ ] Тесты с CDP помечены как Chromium-only.
